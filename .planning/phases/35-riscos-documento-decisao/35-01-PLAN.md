Conteúdo obrigatório por seção:

**Summary:** Uma tabela comparativa das 3 estratégias com colunas: Strategy | Disruption | Timeline | Complexity | Recommended?. Valor da coluna Recommended: "NO", "YES ⭐", "CONDITIONAL".

**Context:** Vida Ativa tem ~200 usuários email/password (hashes SCRYPT no Firebase) + ~30 Google OAuth. Firebase usa SCRYPT com parâmetros exportáveis via CLI. Supabase usa bcrypt nativamente mas suporta verificação multi-algoritmo durante migração.

**Strategy 1 (Forced Reset):**
- How it works: exportar emails Firebase, criar contas Supabase com senha aleatória, enviar email "configure nova senha" para todos
- User impact: ~30% churn típico, usuários percebem plataforma como "quebrada"
- Timeline: ~1 semana (envio emails + suporte)
- Verdict: NOT RECOMMENDED para 200 usuários ativos

**Strategy 2 (JIT Provisioning) — RECOMMENDED:**
- How it works: Firebase ativo em paralelo. Login tenta Supabase → se usuário não existe, cai para Firebase → se Firebase OK, cria usuário em Supabase via admin SDK com `email_confirm: true` → próximo login vai direto para Supabase
- User impact: zero — senha não muda, nenhum email enviado
- Timeline: 60–90 dias para >95% dos usuários ativos migrados automaticamente
- Implementation steps: (1) Firebase SDK permanece no código de login, (2) Middleware tenta Supabase primeiro, (3) Fallback Firebase + provisioning automático, (4) Mapping table: Firebase UID → Supabase UUID, (5) Após 90 dias, desabilitar fallback Firebase
- Incluir código de exemplo TypeScript do 35-RESEARCH.md (seção Gradual Migration)
- Caveat Q2: multi-app race condition documentado como questão aberta
- Verdict: RECOMMENDED — zero disruption, safety net via Firebase

**Strategy 3 (Direct SCRYPT Import):**
- How it works: `firebase auth:export users.json --format=json`, importar via Supabase admin SDK com params SCRYPT exatos
- User impact: zero SE params corretos — senhas funcionam imediatamente; SE params errados → todos fazem reset (pior caso)
- Timeline: ~1 dia (single migration event)
- Critical risks: SCRYPT params base64 fáceis de errar, sem rollback se falhar, teste obrigatório em staging com 10 usuários primeiro
- Verdict: VIABLE como fallback se JIT for descartado; requer teste staging rigoroso

**Google OAuth (~30 users):**
- Re-authentication: Supabase cria nova identity linkada ao mesmo email. Usuário clica "Sign in with Google" na tela de login do novo app.
- User action required: 1 clique ("Sign in with Google") — transparente, nenhum relogin forçado se sessão Firebase ainda válida, mas sessão expira
- Setup requirements: Authentication → Providers → Google no Supabase Dashboard (client ID + secret); Redirect URI: `https://[supabase-url]/auth/v1/callback`; nota sobre Q3 (tokens Firebase em localStorage devem ser limpos no primeiro load pós-cutover)
- Verdict: LOW RISK — processo padrão OAuth2, nenhum dado de senha envolvido

**Recommended Strategy:** Parágrafo explícito declarando JIT Provisioning (Strategy 2) como estratégia recomendada. Justificativa: zero disruption, Firebase como safety net, nenhum usuário recebe email de reset, reversível se algo der errado. Nota: para implementação, contratar mini-spike de migração separado (fora do escopo desta fase).

**Open Questions:** Listar Q1 (Supabase preserva timestamps Firebase?), Q2 (race condition multi-app?), Q3 (Firebase tokens em localStorage pós-cutover)
